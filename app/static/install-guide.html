«Подьячий»: установка и сопровождение

Инструкция для администратора организации. Программировать не нужно; достаточно уметь скопировать файлы на сервер и выполнить несколько команд Docker.

Ставите сервис только для себя, на свой компьютер, — короче и проще инструкция «Установить для себя». Поручить установку ИИ-агенту (Claude Code, Cursor, Codex) — в личном режиме или для организации — можно по файлу install/AI-INSTALL.md: агент спросит, какой режим нужен, и проведёт по этапам.

Для администратора сервиса. Версия сервиса 1.2.0.

1. Что это и что нужно#

«Подьячий» принимает записи совещаний, лекций и созвонов (видео или звук), распознаёт речь с разделением говорящих и пишет по каждой записи расшифровку, протокол и карту протокола. Люди работают с ним через страницу в браузере. Сервис ставится одним контейнером Docker; образ называется egordoronchenko/podyachiy. Сервис — открытый код под лицензией MIT, бесплатный: платить приходится только поставщику моделей.

Распознавание и написание протокола выполняют внешние модели через сервис-поставщик — RouterAI (российский, оплата в рублях) или OpenRouter (зарубежный, оплата в долларах): звук и текст записей уходят за пределы организации — поставщику и владельцам моделей, чьи серверы находятся за границей. Мощный сервер и видеокарта поэтому не нужны.

Сколько стоит обработка. Сам сервис бесплатный; поставщик моделей берёт деньги за распознавание речи и за текст протокола. Ориентир по ценам из карточек моделей: на модели по умолчанию (Scribe v2) — порядка 0,15–0,25 $ за час записи через OpenRouter или 17–30 ₽ через RouterAI; большая часть — распознавание речи. Цены поставщики меняют — сверяйте в их карточках моделей. Платит владелец ключа. Точные расходы сервис показывает администратору в разделе «Расходы» — отдельно в рублях и в долларах, без пересчёта; окончательные цифры — в кабинете поставщика. Расходы видит только администратор сервиса (логин admin и те, кому он дал эту роль): остальным пользователям суммы не показываются ни на страницах, ни запросами.

Сколько нужно места. Сервис хранит три вещи и сам ничего из них не удаляет:

Если люди загружают звук, а не видео, те же 10 часов в неделю займут около 50 ГБ в год. Удалённое лежит в корзине ещё 30 дней (раздел 15), на время загрузки нужен запас на размер загружаемого файла.

2. Установка по шагам#

Шаг 1. Рабочая папка#

Создайте папку, в которой сервис будет жить: например C:\Podyachiy на Windows или /opt/podyachiy на Linux. Положите в неё:

  • compose.yml из комплекта;
  • .env.example из комплекта — и переименуйте его в .env (имя начинается с точки, расширения нет).

Комплект — папка install репозитория: в ней compose.yml, .env.example, Caddyfile.example и эта инструкция. Остальной репозиторий для установки из готового образа не нужен.

Шаг 2. Две обязательные строки в .env#

Откройте .env в текстовом редакторе (Блокнот подойдёт; сохранять в кодировке UTF-8) и заполните:

.env
OPENAI_API_KEY=...ваш ключ поставщика...
ADMIN_PASSWORD=длинный-пароль-главного-администратора

По умолчанию основной поставщик — OpenRouter. Рекомендуемая схема для России — основной RouterAI, запасной OpenRouter (если ключ один — впишите только основного, строки BACKUP_* оставьте пустыми):

.env
OPENAI_BASE_URL=https://routerai.ru/api/v1
OPENAI_API_KEY=...ключ RouterAI...
BACKUP_BASE_URL=https://openrouter.ai/api/v1
BACKUP_API_KEY=...ключ OpenRouter...

Остальное можно не трогать — значения по умолчанию рабочие. Все настройки описаны в разделе 3.

В личном режиме (MODE=personal, раздел 4) входа нет и ADMIN_PASSWORD не нужен.

Файл .env содержит ключ и пароль: дайте доступ к рабочей папке только администраторам сервера.

Шаг 3. Запуск#

В рабочей папке выполните:

bash
docker compose up -d

Первый запуск скачивает образ (около 1 ГБ). Если образ вам передали файлом-архивом, сначала загрузите его: docker load -i имя-файла.tar, затем та же команда.

Шаг 4. Проверка#

  1. docker compose ps — в столбце состояния должно быть Up … (healthy).
  2. Откройте на этом же сервере http://localhost:8081 — появится страница входа.
  3. Войдите: логин admin, пароль — из ADMIN_PASSWORD.
  4. Проверьте ключ поставщика: «Управление → Обработка», кнопка «Проверить ключ». Запрос бесплатный; ответ — принят ключ или нет и есть ли у поставщика текстовые модели из .env. Та же проверка идёт при каждом запуске сервиса — итог строкой в «Журнале работы».
  5. Загрузите короткую запись на две-три минуты (кнопка «Загрузить запись»). Через полминуты она появится в списке со статусом «обрабатывается», ещё через минуту-две — «готово».

После первого запуска в рабочей папке появятся подпапки:

inbox\      исходные записи
outbox\     результаты и лог сервиса
state\      база сервиса podyachiy.db: пользователи, права, ключи доступа, заявки, расходы и журнал действий,
журнал обработки, словари, отметки поручений; рядом — ключ подписи входов и логотип организации
backup\     архивы резервных копий (раздел 12)
prompts\    шаблоны протоколов и словарь терминов

Какая версия сервиса установлена, видно в меню «О сервисе» и в ответе http://localhost:8081/api/status (поле version).

Не открылось — раздел 14.

Остановка и удаление#

docker compose down останавливает и удаляет контейнер; папки с записями, результатами и пользователями остаются. docker compose up -d запускает снова.

Вторая установка на той же машине#

В compose.yml имя проекта Docker задано явно — podyachiy: из папки с русским названием Docker его не выведет. Поэтому вторая установка в другой папке без своего имени считается той же самой: docker compose up -d в ней пересоздаст контейнер первой. Чтобы поставить рядом вторую (например, пробную), в её .env задайте своё имя проекта и свободный порт:

.env
COMPOSE_PROJECT_NAME=podyachiy-test
PORT=8082

Имя — строчные латинские буквы, цифры, дефис. Папки inbox, outbox, state, backup, prompts у каждой установки свои — рядом с её compose.yml. С HTTPS второй установке нужны и свои порты прокси (HTTPS_PORT, HTTP_PORT).

3. Настройки .env#

После любой правки .env выполните docker compose up -d — контейнер пересоздастся с новыми значениями. Записи и пользователи при этом не затрагиваются.

Без папки состояния или папки результатов сервис не запускается (ОТКАЗ ЗАПУСКА: … не подключена с хоста, раздел 14): внутри контейнера они пропали бы при его пересоздании — вместе с базой или с протоколами, за которые уже заплачено. Не подключённые входная папка, папка копий и папка шаблонов — предупреждение в журнале работы и на странице «Обработка»; там же — если на диске какой-то из папок inbox, outbox, state, backup свободно меньше 2 ГБ. Тома и место сервис проверяет при запуске и раз в сутки.

Модели и поставщики#

Менять стоит, только если понимаете зачем: значения по умолчанию проверены.

Поставщиков два, моделей у них одни и те же, называются одинаково. RouterAI — российский шлюз: оплата по счёту в рублях, стоимость в отчётах в рублях. OpenRouter — зарубежный: оплата в долларах, стоимость в отчётах в долларах. Цены у них разные — сравните карточки моделей перед выбором. Рекомендуемая схема для России: основной — RouterAI, запасной — OpenRouter. Запасному уходит вызов, на который основной не ответил (нет связи, ошибка сервера, «слишком много запросов», HTTP 408 — после всех повторов) либо отказал по ключу или деньгам (HTTP 401, 402, 403 — сразу); после этого пять минут запросы идут сразу запасному. Повторы распознавания у одного поставщика — не дольше 20 минут с первой попытки. Не повторяются и запасному не уходят:

  • отказ на сам запрос — прочие ответы 4xx (неверный запрос, нет модели, файл велик): запасной ответил бы так же, причина — в тексте ошибки под записью;
  • у распознавания — таймаут ожидания ответа: файл отправлен, а ответа нет. Поставщик мог уже выполнить работу и списать за неё деньги, и повтор оплатил бы её второй раз. Такую запись сервис повторит целиком по расписанию после сбоя (через полчаса) или её запускают вручную; уже распознанные части длинной записи берутся из сохранённых ответов поставщика и второй раз не оплачиваются.

Запись, которую подхватил запасной, оплачена в его валюте — в разделе «Расходы» рубли и доллары стоят отдельно. Какие поставщики настроены и когда запрос последний раз уходил запасному, видно в разделе «Обработка».

Проверка ключа. Там же кнопка «Проверить ключ»: сервис спрашивает у каждого настроенного поставщика (основного, запасного и отдельного адреса текстовых моделей) сведения о ключе и список моделей и пишет ответ словами — ключ принят, отказ (ключ не принят, исчерпан предел ключа, отказ из-за баланса) или поставщик недоступен; отдельно — если текстовой модели из .env у поставщика нет. Запросы бесплатные: записи не обрабатываются. Та же проверка выполняется один раз при каждом запуске сервиса, итог — строкой в журнале работы; при отказе сервис всё равно запускается. Чего проверка не видит: хватит ли денег на счёте (поставщики не сообщают об этом бесплатным запросом, пока сами не откажут) и открыта ли ключу модель распознавания — это покажет первая запись. Поставщик с незнакомым адресом (своя модель в LM Studio) сведений о ключе не даёт — проверка скажет, что адрес отвечает.

Для организации — только корпоративный. Режим можно сменить позже: записи и протоколы остаются.

Входа в личном режиме нет, поэтому сервис отвечает только по своим адресам: localhost, адресу IP, имени компьютера без точки и адресу из PUBLIC_URL; на другие имена — отказ 400. Так сайт, открытый в браузере на этом же компьютере, не читает сервис. Открываете сервис под своим именем (за прокси) — впишите его в PUBLIC_URL.

Запросы со страниц других сайтов — в обоих режимах. Запрос, который что-то меняет, со страницы другого сайта сервис не выполняет — отказ 403 «запрос пришёл со страницы другого сайта». Чужая страница — заголовок Origin не того адреса, по которому открыт сервис, и не PUBLIC_URL; если Origin срезан, — заголовок Sec-Fetch-Site «cross-site» или «same-site». Так сайт, открытый в том же браузере, не запустит платную обработку от имени вошедшего человека, а вход и заявку на доступ с чужой страницы не отправить. Программы и ИИ-клиенты с ключом или паролем в заголовке Authorization это не затрагивает. За прокси, который меняет заголовок Host (передаёт сервису внутреннее имя), задайте PUBLIC_URL — адрес, по которому сервис открывают люди: иначе все действия на странице получат 403.

5. Сеть: доступ с других компьютеров#

Сразу после установки сервис открывается только с самого сервера. Чтобы пустить людей:

5.1. Открыть сервис в сеть#

В .env:

.env
BIND=0.0.0.0
PUBLIC_URL=http://192.0.2.10:8081

192.0.2.10 замените адресом или именем сервера во внутренней сети, 8081 — своим PORT. Затем docker compose up -d.

5.2. Брандмауэр#

Windows. PowerShell от имени администратора:

PowerShell
New-NetFirewallRule -DisplayName "Podyachiy" -Direction Inbound -Protocol TCP -LocalPort 8081 -Action Allow -Profile Domain,Private

Удалить правило: Remove-NetFirewallRule -DisplayName "Podyachiy". Профиль Public в правило намеренно не включён: в сети, которую Windows считает общественной, порт останется закрыт.

Linux. Docker публикует порт в обход правил ufw и firewalld: после BIND=0.0.0.0 порт, как правило, уже доступен из сети. Если на сервере есть свои запрещающие правила, откройте порт:

bash
# ufw
sudo ufw allow 8081/tcp
# firewalld
sudo firewall-cmd --permanent --add-port=8081/tcp && sudo firewall-cmd --reload

Ограничить доступ одной подсетью на Linux надёжнее всего на сетевом оборудовании или указав в BIND адрес того сетевого интерфейса сервера, который смотрит во внутреннюю сеть.

5.3. Проверить с другого компьютера#

PowerShell
# Windows: в ответе должно быть TcpTestSucceeded : True
Test-NetConnection 192.0.2.10 -Port 8081
bash
# любая система: должен прийти ответ вида {"ok":true,"version":"1.0.0"}
curl http://192.0.2.10:8081/api/status

Затем откройте http://192.0.2.10:8081 в браузере — должна появиться страница входа.

5.4. Что нужно знать про HTTP#

Пока HTTPS не включён (раздел 10), всё идёт по сети открыто, без шифрования:

  • пароли при входе и при смене;
  • ключи доступа ИИ-клиентов — в каждом запросе;
  • ссылки «задать пароль» из писем и пароль, который по ним задают;
  • навык для ИИ-клиентов: по дороге его можно подменить, а клиент выполнит то, что в нём написано;
  • сами протоколы и расшифровки.

Тот, кто может слушать трафик между человеком и сервером, всё это увидит. Это приемлемо только во внутренней сети организации. Через интернет, гостевой Wi-Fi и из дома без VPN сервис по HTTP открывать нельзя.

Ещё одно: права сервиса действуют только на странице. Если папки inbox и outbox открыты людям как сетевые, записи и протоколы читаются там в обход сервиса. Не раздавайте их по сети.

6. Первый вход администратора#

Главный администратор — логин admin, пароль ADMIN_PASSWORD из .env. Он есть всегда, его нельзя удалить, пароль меняется только в .env.

Правило: под admin входят только с самого сервера — по адресу http://localhost:8081, сидя за сервером или через удалённый рабочий стол. По сети этот пароль ходить не должен: его нельзя быстро сменить со страницы, и он открывает всё. Сервис это правило сам не проверяет — его соблюдает администратор.

Что сделать при первом входе:

  1. Войдите на сервере под admin.
  2. «Управление → Пользователи → Добавить пользователя»: заведите себе отдельную учётную запись и отметьте «Администратор сервиса». Пароль — кнопкой «Сгенерировать».
  3. Выйдите и дальше работайте под своей учётной записью — с любого компьютера. Свой пароль вы меняете сами (меню под именем → «Сменить пароль»).
  4. admin оставьте на случай, когда других администраторов не осталось или пароль забыт.

Администраторов сервиса может быть несколько; у них те же права, что у admin.

7. Пользователи, папки, права#

Подробно это описано в справке самого сервиса: пункт «Справка» в меню, разделы «С чего начать» и «Администратору». Коротко:

  • Пользователи («Управление → Пользователи»): логин латиницей, имя, пароль не короче 8 знаков. Пароль показывается один раз — передайте его человеку; сервис хранит только хеш.
  • Личная папка появляется у каждого сама: её видят он и администраторы сервиса. Загружать в неё записи человек может, только если в его учётной записи стоит галочка «Загрузка в личную папку» (у нового пользователя её нет).
  • Общие папки («Управление → Папки и доступ») создаёт администратор сервиса. У каждой папки кнопка «Доступ» открывает таблицу: кому что можно.
  • Три права на папку, каждое включает предыдущие: чтение (видеть записи, протоколы, поиск, поручения, скачивать протокол), загрузка (ещё и класть новые записи) и администрирование (ещё и раздавать чтение и загрузку, подписывать ФИО говорящих, пересобирать протокол). У каждого права область: только эта папка или папка со всеми подпапками. Администраторов папок назначает только администратор сервиса.
  • Чтение загружать не разрешает. Обработка каждой записи стоит денег у поставщика, поэтому загрузку вы выдаёте отдельно — тем, кому доверяете тратить. Пересборка протокола тоже платная и требует права загрузки.
  • Удаление пользователя не трогает его папку и записи.
  • Входы. Вход на странице помнится 30 дней. Человек сам завершает свои входы на других браузерах и устройствах — меню под именем → «Выйти везде» (этот браузер остаётся во входе). Администратор сервиса завершает все входы человека кнопкой «Завершить входы» в его строке раздела «Пользователи» — например, когда тот потерял ноутбук; войти заново человек может своим паролем. Ни то ни другое ключей доступа не отзывает: ключи отзываются в окне «Ключи доступа» или в блоке «Ключи доступа» раздела «Пользователи». При смене пароля и при задании пароля по ссылке есть флажок «Отозвать мои ключи доступа» (по умолчанию выключен: на ключах работают программы человека). Входы admin из .env кнопкой «Завершить входы» не завершить — он делает «Выйти везде» сам; смена ADMIN_PASSWORD в .env тоже завершает все его входы.

7а. Шаблоны, словарь и оформление#

Раздел «Управление → Настройки»; подробности — в справке сервиса, «Администратору».

Шаблоны и словарь (оба режима). Шаблон — задание модели, по которому она пишет протокол; у каждого типа записи свой. На странице шаблон можно посмотреть, поправить в поле правки, скачать и загрузить файлом (.md или .txt в UTF-8, до 256 КБ), сравнить со стандартным и вернуть стандартный. Прежний текст при каждом изменении сохраняется — две последние версии можно вернуть со страницы. Там же правятся словарь терминов, задание на разбор записи и задание на выписку поручений. Можно добавить свой тип записи: название, одно-два предложения «когда применять» и шаблон; разбор записи будет выбирать и его.

  • Правка действует со следующей записи, перезапуск не нужен. Готовые протоколы не меняются; одну запись пересобирают ручным запуском в разделе «Обработка» (без галки «перезаписать» — платится только текст протокола).
  • Всё это — файлы в папке prompts: шаблоны *.md, словарь glossary.txt, свои типы types.json, прошлые версии в подпапке history. Править их можно и обычным редактором на сервере — страница покажет то, что лежит в файлах. Сохраняйте файлы в кодировке UTF-8.
  • Если папка prompts подключена только для чтения (:ro в compose.yml), страница покажет шаблоны, но сохранить правку не сможет.
  • Общие правила шаблонов — файл prompts/common.md, на странице — «Общие правила шаблонов». Правила, одинаковые в нескольких шаблонах, лежат в нём один раз, кусками с именами: кусок начинается строкой @@ имя. Строка @@ имя в шаблоне при обработке заменяется этим куском, поэтому правка куска действует во всех шаблонах, которые его подключают. Шаблон без таких строк собирается как есть. Кусок, который подключает хоть один шаблон, из общего файла не убрать — сохранение откажет и назовёт шаблоны; сначала уберите строку @@ … из них. Сам общий файл модели не уходит — только куски в составе шаблонов.

Словарь папки и записи (оба режима). Общий словарь из «Настроек» один на всех. Имена и сокращения у каждого отдела свои, поэтому у каждой папки и у каждой записи есть свой словарь: кнопка «Словарь» в открытой папке и в открытой записи, а при загрузке — «Словарь записи» у строки загрузки.

  • В словаре два списка, по строке на запись: участники («ФИО — должность», в скобках после ФИО — как ещё называют) и сокращения («как писать — расшифровка»). Список можно вставить из приглашения на встречу или из таблицы. В одном словаре — до 200 участников и до 300 сокращений.
  • Словарь папки действует на её записи и записи подпапок. Словарь записи дополняет словарь папки, тот — словари папок выше и общий словарь; при совпадении побеждает ближний к записи.
  • Читает словарь тот, кому открыта папка; правит владелец личной папки, администратор общей и администратор сервиса. В личном режиме ограничений нет.
  • Что делает обработка: текстовая модель сводит имена из записи к ФИО из списка (только при уверенном совпадении по звучанию и роли) и пишет сокращения как в словаре. Кого в записи не слышно, в протокол не попадает: список — подсказка, а не перечень присутствующих. Модели распознавания, которая принимает подсказки (Microsoft MAI-Transcribe 2), термины и имена уходят ещё и списком фраз — не больше 500, каждая до 60 знаков; сначала словарь записи, затем папки, затем общий. Остальным моделям распознавания подсказать нечем — словарь правит только протокол.
  • Правка действует со следующей обработки. Готовые протоколы не меняются: протокол записи пересобирают кнопкой «Сохранить и пересобрать протокол» в её словаре (хозяин папки, у которого есть ещё и право загрузки; платится только текст, речь заново не распознаётся). Чтобы подсказки дошли до распознавания уже готовой записи, её запускают заново целиком — раздел «Обработка», галка «перезаписать», модель MAI; это стоит как новая запись и сбрасывает подписи говорящих.
  • Пересборка — одна на набор правок. Подписи говорящих и словарь сохраняются сразу и бесплатно. Повторная просьба второй пересборки не ставит: пока первая ждёт в очереди — никогда; пока она идёт — только если подписи или словарь с её начала правили, и только одну.
  • Словарь пополняется из подписей говорящих. ФИО, подписанное у говорящего в записи, сервис сам добавляет в словарь папки этой записи (без должности), если такого человека нет ни в нём, ни в словарях папок выше: так его узнают следующие записи папки. Берётся только ФИО — от двух до четырёх слов с заглавной буквы, а не «Иван» и не «представитель заказчика». У записей в корне словаря папки нет — там словарь не пополняется. Пересборок это не запускает; сколько добавлено — в журнале действий, в событии о подписи говорящих.
  • Словари лежат в базе сервиса (state/podyachiy.db) — входят в резервную копию. При переименовании и переносе папки или записи словарь переезжает следом; у удалённой — уходит с ней в корзину и возвращается вместе с ней.
  • Изменение словаря пишется в журнал действий: кто, где, сколько строк — без самих имён.

Оформление (только корпоративный режим, вкладка «Оформление»). Логотип организации — в меню, на странице входа и значком вкладки; короткое название организации — рядом с логотипом, в заголовке вкладки, в письмах и в колонтитуле скачиваемых протоколов.

  • Файл логотипа: PNG, JPEG или WebP, до 2 МБ, меньшая сторона не меньше 256 точек, большая — не больше 4096. SVG и GIF не принимаются (в SVG может быть сценарий). Лучше квадрат на прозрачном фоне, без мелких надписей.
  • Картинки логотипа лежат в state/brand, название организации — в базе сервиса; и то и другое входит в резервную копию.
  • «Вернуть стандартный» убирает логотип и название.

8. Почта и заявки на доступ#

Заявка на доступ работает и без почты: человек нажимает «Запросить доступ» на странице входа (почта в форме тогда необязательна), заявка появляется у администратора в «Пользователи → Заявки на доступ» и счётчиком в меню. После «Открыть доступ» сервис показывает администратору одноразовую ссылку «задать пароль» на 48 часов — её и логин он передаёт человеку сам; новую ссылку выпускает кнопка «Показать ссылку» в строке пользователя. PUBLIC_URL для этого не нужен: ссылка строится от адреса, по которому администратор открыл страницу. «Забыл пароль» без почты на странице входа нет — вместо него написано обратиться к администратору.

С почтой ссылка уходит человеку письмом, работает «Забыл пароль», люди получают письмо, когда их запись готова, и могут отправить протокол на почту.

  1. Впишите в .env: SMTP_HOST; при необходимости SMTP_PORT, SMTP_SECURITY, SMTP_CA_FILE, SMTP_USER, SMTP_PASSWORD, SMTP_FROM; обязательно PUBLIC_URL; ADMIN_EMAIL — кому сообщать о заявках; MAIL_DOMAINS — домен почты организации: с адресами вне него заявка на доступ не примется и протокол на почту не уйдёт (см. ниже «Протокол на почту»).
  2. docker compose up -d.
  3. Войдите администратором: «Пользователи → Почта → Отправить пробное письмо». Оно уходит на почту из вашей учётной записи, а если её нет — на ADMIN_EMAIL. Не дошло — там же показан ответ почтового сервера как есть.

Почта включается, когда заданы SMTP_HOST, SMTP_FROM (или SMTP_USER) и PUBLIC_URL. Если чего-то не хватает, причина написана в блоке «Почта» и в логе при запуске.

SMTP_FROM — адрес или имя с адресом: SMTP_FROM=Подьячий <podyachiy@example.ru>; с именем письмо в ящике подписано понятнее.

Сертификат почтового сервера. При starttls и ssl сервис проверяет сертификат сервера. SMTP_HOST должен совпадать с именем в сертификате: полное имя сервера (mail.example.ru), а не адрес и не короткое имя. Если сертификат выдан внутренним центром сертификации организации, пробное письмо ответит CERTIFICATE_VERIFY_FAILED: положите корневой сертификат этого центра (PEM) в папку состояния — например, под именем smtp-ca.pem — и укажите путь внутри контейнера: SMTP_CA_FILE=/data/state/smtp-ca.pem. Файла по этому пути нет — почта выключена, причина написана в блоке «Почта» и в логе.

Без защиты. SMTP_SECURITY=none вместе с SMTP_USER означает, что логин и пароль почты идут до сервера открытым текстом. Сервис так работает, но пишет об этом строкой «ВНИМАНИЕ» в логе при запуске и заметкой в блоке «Почта».

Если письмо не ушло. Когда почтовый сервер не принял письмо со ссылкой «задать пароль» («Открыть доступ», «Выслать ссылку»), сервис показывает ссылку администратору — как без почты — вместе с ответом сервера: человеку её можно передать самому, не дожидаясь починки почты. Каждое не ушедшее письмо — о заявке, со ссылкой, о готовности записи, протокол — остаётся строкой в логе и событием в журнале действий с ответом сервера. Тому, кто отправляет протокол, текст ошибки не показывается: он видит «почтовый сервер не отвечает — сообщите администратору сервиса» либо адреса, которые сервер не принял, с ответом сервера по каждому.

Как это работает дальше:

  • на странице входа рядом с «Запросить доступ» появляется «Забыл пароль», почта в заявке становится обязательной, а с заданным MAIL_DOMAINS — только из доменов организации;
  • заявка приходит письмом на ADMIN_EMAIL и счётчиком у пункта «Пользователи»; «Ответить» в этом письме ведёт к заявителю;
  • «Открыть доступ» заводит пользователя с личной папкой (загрузку в неё разрешает галочка в заявке или потом в учётной записи); ему уходит письмо с логином и одноразовой ссылкой «задать пароль» на 48 часов. Пароль в письме не пересылается;
  • «Отклонить» убирает заявку, письмо человеку не шлётся — об этом сказано на странице после подачи заявки;
  • уже заведённым пользователям впишите почту в учётную запись — иначе «Забыл пароль» для них не сработает.

Формы заявки и сброса пароля открыты без входа, поэтому ограничены: 5 заявок в час с одного адреса, 3 сброса в час на один логин. В Docker Desktop на Windows все посетители приходят к сервису с одного адреса, и предел в 5 заявок в час становится общим на всех.

Форма заявки не подсказывает, какие логины и почты уже заведены. Заявка с занятым логином ложится как обычная: при «Открыть доступ» сервис скажет, что логин занят, и его можно поправить. Заявку с почтой, которая уже есть у учётной записи, сервис не сохраняет, а владельцу этого ящика пишет, что учётная запись у него уже есть, с его логином и ссылкой «Забыл пароль»; заявитель видит тот же ответ, что и все. Без почты в сервисе такая заявка ложится, и отказ будет виден при одобрении.

Почта включена, а MAIL_DOMAINS не задан — в журнале работы при запуске и в блоке «Почта» раздела «Пользователи» предупреждение: заявку принимают с любой почтой (на неё после одобрения уйдёт ссылка «задать пароль»), а протокол можно отправить на любой адрес. С заданным MAIL_DOMAINS в журнале строка заявки на доступ принимаются и протокол со страницы записи отправляется только на адреса доменов: ….

Письмо «запись готова»#

Когда обработка записи закончилась, сервис пишет тому, кто её загрузил: название, длительность, число поручений, раздел «Кратко» протокола и ссылка на запись. Письмо уходит, если у человека в учётной записи указана почта и он не отключил письма в меню учётной записи («Письма о готовности»; включено, пока человек сам не отключит).

  • На запись — одно письмо о готовности: пересборка протокола и повторы после сбоя второго письма не шлют.
  • Если запись обработать не удалось, письмо о сбое приходит один раз — когда сервис перестал повторять сам (три сбоя подряд) либо сразу, если в файле нет звука. В письме сказано, что случилось и что делать; текста ошибки в нём нет, причина — в разделе «Обработка».
  • Ручной запуск из раздела «Обработка»: письмо об исходе получает тот, кто запустил, а не автор; о сбое ему написано, что причина — под записью в разделе «Обработка».
  • У admin из .env почты нет — заведите себе обычную учётную запись с почтой, если хотите получать письма о своих запусках.
  • Письмо уходит отдельно от обработки: если почтовый сервер не ответил, запись остаётся готовой, а в логе и в журнале действий появляется строка «письмо … не ушло».

Напоминания о сроках поручений#

Раз в день, после 8:00 по часам сервиса (TZ), сервис пишет каждому, у кого в учётной записи есть почта, сводку его поручений: просроченные, со сроком сегодня и со сроком завтра — только из папок, открытых этому человеку, и только незакрытые. Нечего напомнить — письма нет. Просроченное — по сроку, заданному вручную (как отбор «только просроченные»); «сегодня» и «завтра» — ещё и по дате, которую сервис вычислил из слов протокола, — в письме тогда приведены и сами слова.

  • Чьё поручение. Исполнитель в протоколе сличается с ФИО учётной записи: фамилия — отдельным словом, остальные слова — имя или отчество человека, буквы — их инициалы («Иванов И. П.»). Поручение на метку голоса («S2») не напоминается никому — подпишите говорящих и пересоберите протокол.
  • Включены у всех с почтой, пока человек сам не отключит — меню под именем → «Напоминания о сроках». После обновления до 1.2.0 — тоже у всех: если они не нужны организации, предупредите людей, как отключить, или не вписывайте почту в учётные записи.
  • В письме — до 50 поручений в каждой части и ссылка на страницу «Поручения» с отбором по фамилии человека. Строка журнала работы — напоминания о сроках поручений: писем N; не ушедшее письмо — ВНИМАНИЕ: напоминание о сроках поручений для <логин> не ушло: … и событие в журнале действий.
  • У admin из .env почты нет — напоминаний ему нет.

Протокол на почту — куда он может уйти#

В открытой записи у хозяина папки (владелец личной, администратор общей, администратор сервиса) есть кнопка «Отправить»: протокол уходит письмом — файлом PDF или DOCX либо только ссылкой. Получателей он вписывает сам; сервис подсказывает тех, кому папка открыта.

Это отправка содержимого совещания за пределы сервиса, на произвольные адреса. Что её ограничивает:

  • MAIL_DOMAINS в .env — список почтовых доменов через запятую. Если он задан, адрес вне списка сервис не примет. Пока список пуст, протокол можно отправить на любой адрес, в том числе на личную почту вне организации. Задайте домен почты организации: MAIL_DOMAINS=example.ru. Домен сверяется целиком: example.ru не открывает sub.example.ru. При запуске в логе сказано, какое правило действует. Тот же список ограничивает и почту в заявке на доступ.
  • Отправляет только хозяин папки; тому, у кого папка открыта на чтение, кнопки нет.
  • Ключом доступа (ИИ-клиент) отправить нельзя — только самому человеку на странице.
  • За раз — не больше 20 получателей, в час — не больше 10 отправок на человека, вложение — до 10 МБ. В предел идут только удавшиеся отправки: письмо ушло хотя бы одному адресу.
  • Каждая отправка пишется в журнал действий («Расходы» → журнал; хранится в базе сервиса): кто, какая запись, адреса получателей полностью, формат вложения. Неудачные отправки — тоже.

Каждому получателю уходит отдельное письмо: адресов друг друга они не видят, а ответ на письмо придёт отправителю, если у него в учётной записи указана почта. Если часть адресов почтовый сервер не принял, остальным письмо всё равно уходит; страница и журнал действий называют, кому нет. Ссылка в письме открывается только у того, у кого есть учётная запись в сервисе и доступ к папке записи; вложение читается без сервиса. Запретить отправку совсем можно, только выключив почту.

Почта проверена на тестовом почтовом сервере: без защиты, со STARTTLS и SSL, со входом по логину. С почтовым сервером организации не проверялась — начните с пробного письма. Как письмо и вложение с именем кириллицей выглядят в Outlook и веб-почте, не проверялось — посмотрите на первом же отправленном протоколе.

9. Интеграция с ИИ#

Люди могут просить своего ИИ-клиента (Cursor, Claude Code, Codex и другие клиенты с терминалом) найти протокол, собрать поручения или загрузить запись. Клиенту для этого ставится навык — короткая инструкция, которую раздаёт сам сервис.

Что нужно от администратора:

  1. PUBLIC_URL обязателен. Этот адрес вписывается в навык. Без него в навык попадёт адрес, по которому пришёл запрос, — например localhost, и у людей ничего не заработает.
  2. Сервис должен быть виден с компьютеров людей (раздел 5).
  3. Дальше каждый делает сам по разделу справки «Интеграция с ИИ»: выбирает, чем подключаться (ключ доступа — лучше — или логин и пароль), вставляет в чат клиента одну фразу, выпускает себе ключ (кнопка в справке или меню под именем → «Ключи доступа») и вписывает его в файл .podyachiy в своей домашней папке.

Что полезно знать:

  • ключ даёт клиенту права его владельца: читать записи, загружать (если у владельца есть право загрузки — у читателя ключ тоже только читает), переименовывать и переносить их, подписывать говорящих, отмечать поручения, править словарь и текст протокола там, где человек хозяин папки. Удалять записи и возвращать их из корзины, управлять сервисом и смотреть расходы обычным ключом нельзя;
  • ключ выпускает себе каждый, и вы под логином admin тоже;
  • ключ «с управлением» — флажок в окне ключей, только у администраторов сервиса, срок не дольше 90 дней. Клиент с ним может заводить пользователей, раздавать права на папки, принимать заявки, смотреть расходы. Утёкший, он опасен так же, как ваш пароль, — выпускайте на короткий срок и отзывайте после работы. Даже им нельзя: выпускать и отзывать ключи, задавать пароли (и новому пользователю тоже — заведённому ключом пароль задаётся ссылкой, которую вы выпускаете на странице) и получать ссылки на пароль, назначать и снимать администраторов сервиса, менять почту пользователей, удалять записи и папки и возвращать их из корзины, отправлять протокол на почту, править шаблоны и оформление, проверять подключение к домену и привязывать к нему учётные записи. Так утёкший ключ не становится входом на страницу ни под чьим именем. Завершить входы пользователя (POST /api/admin/users/sessions), поставить расписание резервной копии и снять запись из очереди им можно;
  • все ключи сервиса видны вам в разделе «Пользователи», блок «Ключи доступа»: чей, вид, когда создан, когда использован, когда истекает. Истёкшие и не использовавшиеся 90 дней помечены; любой ключ можно отозвать. Действия по ключу в журнале стоят с его именем и видом;
  • ключи человек отзывает и сам — в окне «Ключи доступа» или флажком «Отозвать мои ключи доступа» при смене пароля; у удалённого пользователя они перестают действовать. «Выйти везде» и «Завершить входы» ключей не отзывают;
  • ключи лежат в базе сервиса (отпечатки, не сами ключи). После обновления с версии без базы сервис при первом запуске переносит их сам (раздел 13);
  • навык обновляет себя сам: после обновления сервиса клиенты при первом обращении скачивают новую версию. Навык, поставленный до этого (версия 3 и более ранние), один раз ставится заново — той же фразой из справки;
  • свои программы ходят в сервис теми же ключами. Методы, параметры и примеры запросов — на странице /api (ссылки — в справке и в окне «Ключи доступа»); то же в виде OpenAPI 3.1 — /api/v1/openapi.json;
  • в личном режиме (MODE=personal) ключей нет и не нужно: навык работает без входа;
  • без входа сервис данных не отдаёт. Открыты только навык (/skill: в нём адрес сервиса и описание запросов), описание API (страница /api и /api/v1/openapi.json: методы, параметры и примеры — без данных и настроек установки; адрес в них — PUBLIC_URL), пустые оболочки страниц с их скриптами и стилями (содержимое приходит запросами после входа) и три служебных ответа: /api/status (сервис жив, номер версии), /api/me (вошёл ли человек и какие способы входа включены) и /api/brand (название и логотип организации для страницы входа). Открыты ещё форма заявки на доступ и страница «задать пароль» по одноразовой ссылке, а с почтой — и форма сброса пароля;
  • облачные ассистенты (чат в браузере) до сервиса во внутренней сети не достанут.

Если клиент не может достучаться до сервиса с компьютера человека:

  • Codex — в файле ~/.codex/config.toml:

    toml
    [sandbox_workspace_write]
network_access = true

  • Cursor — в файле ~/.cursor/sandbox.json:

    json
    {"networkPolicy": {"allow": ["192.0.2.10"]}}

Эти настройки взяты из документации клиентов. Установка навыка проверена в Cursor; в Codex и Claude Code — нет.

По HTTP ключ идёт открыто, а навык можно подменить по дороге (раздел 5.4). Во внутренней сети это допустимо; надёжно — только с HTTPS.

9а. Webhook для внешних систем#

Внешняя система — 1С, трекер задач, свой сценарий — может узнавать о готовых записях сама: сервис шлёт ей POST с JSON, когда запись готова (record.ready) или обработать её не удалось (record.failed: в файле нет звука или сбои кончились и запись ждёт администратора). Опрашивать GET /api/v1/records?since=… тогда не нужно. Событие одно на исход записи: пересборка протокола и повтор готовой записи событий не дают.

Включить. В .env — две строки, затем docker compose up -d:

.env
WEBHOOK_URL=https://erp.example.ru/podyachiy/hook
WEBHOOK_SECRET=длинная-случайная-строка-та-же-что-у-получателя

Несколько получателей — адреса через запятую. Без секрета webhook выключен: в журнале работы строка ВНИМАНИЕ: webhook выключен — WEBHOOK_SECRET не задан…. Включённый — строка webhook «запись готова» включён: https://erp.example.ru (в журнале и на странице адрес показан без пути и параметров: в них бывает токен).

  • Подпись. Тело подписано: X-Podyachiy-Signature — sha256= и HMAC-SHA256 секретом от строки «время.тело», X-Podyachiy-Timestamp — время попытки. Получатель сверяет подпись и отвергает старые запросы. Формат тела и пример проверки на Python — на странице /api сервиса, раздел «Webhook». Секрет короче 16 знаков — предупреждение в журнале.
  • https:// или http://. По http:// сервис доставляет, но предупреждает при запуске: тело (названия и пути записей) видно в сети; подделать его без секрета нельзя. Получатель во внутренней сети без сертификата — допустимо; наружу — только https://.
  • Ссылки на запись в теле строятся от PUBLIC_URL; без него — предупреждение, ссылки от корня сайта.
  • Доставка. Ответ 2xx — доставлено. Иначе или без ответа за 10 секунд — повтор через 1, 5 и 30 минут, 2 и 12 часов. Очередь доставки лежит в базе и переживает перезапуск сервиса; доставка «хотя бы раз»: изредка событие приходит дважды с одним id — получатель отбрасывает повтор. Доставки старше суток (сервис долго стоял) и на адреса, которых больше нет в WEBHOOK_URL, при запуске снимаются.
  • Где состояние. Поле webhook в GET /api/admin/status (ключ «с управлением»): сколько доставок ждёт, ближайшая попытка, последняя доставка и последний сбой.

Строки журнала работы — не о каждой попытке, а о переменах:

СтрокаЧто значит
ВНИМАНИЕ: webhook на … не доставлен (…) — повторю через 1 мин; дальнейшие сбои на этот адрес в журнал не пишутся, пока доставка не пойдётпервый сбой доставки на адрес: получатель не ответил или ответил не 2xx
webhook на …: доставка снова идётпосле сбоев получатель снова принимает
ВНИМАНИЕ: webhook record.ready по записи … на … не доставлен: …; попыток 6 за … ч — больше не повторяюдоставка снята после последней попытки: получатель о записи не узнал — пусть возьмёт её из GET /api/v1/records?since=…

10. Включить HTTPS#

HTTPS шифрует всё, что перечислено в разделе 5.4. Его даёт прокси Caddy — второй контейнер, который принимает людей по https:// и передаёт запросы сервису. В compose.yml он уже описан, но выключен (закомментирован).

Понадобится: имя сервера в DNS организации (например podyachiy.example.ru), указывающее на адрес сервера, и сертификат на это имя.

Шаг 1. Сертификат#

Основной случай — сертификат от центра сертификации организации. Попросите у администраторов сертификат на имя сервера и положите два файла в папку certs рядом с compose.yml:

certs\podyachiy.crt    сертификат сервера, следом за ним — промежуточные сертификаты (формат PEM)
certs\podyachiy.key    закрытый ключ к нему (формат PEM, без пароля)

Если сертификат выдали одним файлом .pfx, его нужно разложить на эти два файла — это делают те, кто выдал сертификат.

Два других случая — сертификата нет (Caddy выпускает сам, браузеры предупреждают, пока его корневой сертификат не установлен на компьютеры) и публичное имя с Let's Encrypt — описаны прямо в Caddyfile.example.

Шаг 2. Файл Caddyfile#

Скопируйте Caddyfile.example в рабочую папку под именем Caddyfile (без расширения). Оставьте в нём один вариант из трёх и замените podyachiy.example.ru своим именем. Для основного случая получится:

podyachiy.example.ru {
tls /certs/podyachiy.crt /certs/podyachiy.key
reverse_proxy podyachiy:8080
}

podyachiy:8080 менять не нужно: это сервис внутри Docker.

Проверьте файл до запуска (команда выполняется в рабочей папке; на Windows — в PowerShell):

bash
docker run --rm -v "./Caddyfile:/etc/caddy/Caddyfile:ro" -v "./certs:/certs:ro" caddy:2 caddy validate --config /etc/caddy/Caddyfile

В конце должно быть Valid configuration.

Шаг 3. Включить прокси в compose.yml#

Откройте compose.yml, найдите в конце блок, начинающийся со строки # caddy:, и в каждой его строке до конца файла уберите решётку и один пробел после неё. Строка caddy: должна оказаться с тем же отступом (два пробела), что и строка podyachiy: выше. Пояснения над блоком трогать не нужно.

Проверка: docker compose config --services должна вывести две строки — podyachiy и caddy.

Шаг 4. .env#

.env
BIND=127.0.0.1
PUBLIC_URL=https://podyachiy.example.ru

BIND=127.0.0.1 закрывает прямой вход по HTTP из сети: остаётся только путь через прокси. PUBLIC_URL с https:// нужен, чтобы ссылки в письмах и навык вели на защищённый адрес.

Шаг 5. Запуск и проверка#

bash
docker compose up -d
docker compose ps
docker compose logs caddy --tail 20
  • Откройте порты 443 и 80 в брандмауэре (как в разделе 5.2, с номерами 443,80) и закройте прежний порт 8081: на Windows — Remove-NetFirewallRule -DisplayName "Podyachiy".
  • С другого компьютера: curl https://podyachiy.example.ru/api/status должен ответить {"ok":true,"version":"…"} без ошибок сертификата; в браузере у адреса — замок.
  • http://podyachiy.example.ru должен сам перевести на https://.
  • Скажите людям новый адрес. Тем, кто ставил навык для ИИ-клиента, нужно поправить строку url= в своём файле .podyachiy; ключи доступа стоит перевыпустить — прежние ходили по сети открыто. По той же причине стоит попросить людей сменить пароли.

Что учесть#

  • Порты 443 и 80 на сервере должны быть свободны. Заняты — задайте другие в .env: HTTPS_PORT=8443, HTTP_PORT=8080; адрес тогда будет вида https://podyachiy.example.ru:8443, а автоматический перевод с http:// работать не будет — давайте людям полный адрес.
  • Сертификат организации Caddy сам не продлевает: до истечения срока замените два файла в certs и выполните docker compose restart caddy.
  • Папка caddy в рабочей папке — служебная, её не удаляют.
  • По HTTPS сервис отдаёт заголовок Strict-Transport-Security на год: браузер, раз открывший сервис по https://, дальше сам не пойдёт на него по http://. Возвращаться на HTTP после включения HTTPS не стоит. За прокси сервис узнаёт, что запрос пришёл по HTTPS, только от адреса из FORWARDED_ALLOW_IPS (ниже): без этой настройки заголовка нет.
  • Если прокси передаёт сервису своё внутреннее имя в заголовке Host, задайте PUBLIC_URL — иначе действия на странице получат отказ 403 (раздел 4). Caddy из комплекта Host не меняет.
  • За прокси сервис видит всех посетителей с одного адреса — адреса прокси, поэтому предел «5 заявок на доступ в час с одного адреса» становится общим на всех. Чтобы сервис различал посетителей, в .env задают FORWARDED_ALLOW_IPS=<адрес контейнера caddy>; звёздочку ставить нельзя. Адрес контейнеру назначает Docker; чтобы он не менялся, его закрепляют — как это сделать, написано в разделе 10а, шаг 1. Для внутренней сети общий предел обычно не мешает, но для входа через домен эта настройка обязательна: по ней сервис узнаёт, что человек пришёл по HTTPS.

Что проверено: файл compose.yml с включённым блоком и все три варианта Caddyfile проходят проверку синтаксиса; связка «Caddy с собственным сертификатом → сервис» отвечала по HTTPS и переводила с HTTP. С сертификатом настоящего центра сертификации организации не проверялось.

10а. Вход через домен (Active Directory)#

Только корпоративный режим. Люди входят в сервис тем же логином и паролем, что на рабочем компьютере: вводят их на странице входа сервиса, а сервис проверяет их у контроллера домена по протоколу LDAP. Пароль в сервисе не хранится. Единого входа Windows («без ввода пароля») нет.

Что при этом происходит:

  • при первом входе человек заводится в сервисе сам: логин (как в домене, строчными буквами), ФИО и почта из домена, личная папка — без права загрузки: его, как и права на общие папки, выдаёте вы. При каждом следующем входе ФИО и почта обновляются;
  • кого пускать, решает группа доступа в домене; кто администратор сервиса — группа администраторов. Вложенные группы учитываются;
  • вошедшего сервис сверяет с доменом раз в 15 минут: отключили учётную запись или убрали из группы — доступ пропадает не позже чем через 15 минут, вместе с ключами доступа человека;
  • встроенный admin и локальные учётные записи (заведённые на странице «Пользователи») входят как раньше — это запасной вход на случай, если домен недоступен. Пароль admin храните.

Почему нужен HTTPS. Доменный пароль открывает человеку почту, файлы и всё остальное в сети организации. По HTTP он шёл бы от браузера до сервиса открытым текстом, и его мог бы прочитать любой, кто слушает сеть. Поэтому вход через домен принимается только по https:// (и с самого сервера), а до контроллера домена сервис ходит только по шифрованному соединению и проверяет его сертификат. По http:// страница входа доменный вход не предлагает, а попытка получает отказ.

Шаг 0. Что подготовить в домене#

Это делает администратор домена.

  1. Служебная учётная запись — обычный пользователь домена, например svc-podyachiy, с длинным паролем и галочкой «Срок действия пароля не ограничен». Особых прав не нужно: любой пользователь домена и так читает каталог. В группы администраторов её не включать. Ею сервис ищет людей и читает их группы; менять в домене она ничего не может.
  2. Группа доступа, например Podyachiy-Users: кто в неё входит (сам или через вложенную группу), тот может войти в сервис.
  3. Группа администраторов сервиса, например Podyachiy-Admins — необязательно. Сделайте её членом группы доступа либо добавьте администраторов в обе.
  4. Корневой сертификат центра сертификации организации, которым подписан сертификат контроллера домена, — файл в формате PEM (текст -----BEGIN CERTIFICATE-----). В Windows: certutil -ca.cert corp-root.cer, затем certutil -encode corp-root.cer ldap-ca.pem. У контроллера должен быть сертификат для LDAPS (порт 636) — в домене с центром сертификации он выдаётся контроллерам автоматически.
  5. Полное имя контроллера (dc1.corp.local) должно находиться с сервера сервиса, а порт 636 контроллера — быть открыт для него.

Основную группу человека (обычно «Пользователи домена») домен членством не считает: назначить её группой доступа нельзя — заведите отдельную.

Шаг 1. HTTPS и адрес прокси#

Включите HTTPS по разделу 10. Затем сервису нужно знать адрес прокси, чтобы верить его словам «человек пришёл по HTTPS». В compose.yml, в блоке caddy: и в самом конце файла, есть закомментированные строки с пометкой «для входа через домен» — раскомментируйте их: они закрепляют за прокси адрес 172.31.250.2. В .env добавьте:

.env
FORWARDED_ALLOW_IPS=172.31.250.2

После этой правки сеть контейнеров создаётся заново: выполните docker compose down, затем docker compose up -d (записи и пользователи не затрагиваются). Если подсеть 172.31.250.0/24 в вашей сети занята, замените её в compose.yml и в .env на свободную. Звёздочку в FORWARDED_ALLOW_IPS не ставьте: тогда «я пришёл по HTTPS» сможет сказать кто угодно.

Шаг 2. Корневой сертификат#

Положите ldap-ca.pem в папку состояния сервиса (state в рабочей папке) — под этим именем сервис найдёт его сам. Другое место — путь внутри контейнера в LDAP_CA_FILE.

Шаг 3. Строки в .env#

.env
LDAP_URL=ldaps://dc1.corp.local:636,ldaps://dc2.corp.local:636
LDAP_BASE_DN=DC=corp,DC=local
LDAP_BIND_DN=CN=svc-podyachiy,OU=Service,DC=corp,DC=local
LDAP_BIND_PASSWORD=пароль служебной учётной записи
LDAP_ACCESS_GROUP=Podyachiy-Users
LDAP_ADMIN_GROUP=Podyachiy-Admins
LDAP_DOMAIN=CORP
  • В LDAP_URL — полные имена контроллеров, как они записаны в их сертификатах, не адреса. Контроллеров может быть несколько: не ответил первый — сервис идёт к следующему.
  • LDAP_BIND_DN — DN целиком (в оснастке «Пользователи и компьютеры»: свойства → редактор атрибутов → distinguishedName) либо svc-podyachiy@corp.local.
  • Группы — именем или DN целиком. Имя ищется под LDAP_BASE_DN.
  • Пароль служебной учётной записи лежит только в .env: на странице и в журналах его нет. Если в пароле есть пробел, #, $ или кавычки, заключите его в одинарные кавычки — иначе Docker прочитает строку по-своему, и служебная запись «не будет принята».

Выполните docker compose up -d.

Шаг 4. Проверить кнопкой#

Войдите как admin, откройте «Управление → Пользователи», блок «Вход через домен». Там видно, включён ли вход (и если нет — почему) и с какими параметрами. Нажмите «Проверить подключение»: сервис пройдёт по шагам — соединение с каждым контроллером (чей сертификат, кем выдан, до какого числа действует), служебная учётная запись, база поиска и сколько в ней людей, обе группы и сколько в них людей. У каждого отказа написано, что делать.

В той же форме можно проверить вход конкретного человека: впишите его логин и пароль. Пароль уходит в домен на проверку и нигде не сохраняется; учётная запись в сервисе при этом не заводится.

Потом откройте сервис по https:// и войдите доменным логином. Логин принимается в любом виде: ivanov, CORP\ivanov, ivanov@corp.local.

Подпись LDAP и привязка канала. Это две политики контроллера домена. «Требования к подписыванию LDAP-сервера: требовать подпись» запрещает передавать пароль по незашифрованному соединению — контроллер отвечает strongerAuthRequired. Сервису это не мешает: по LDAPS (и по StartTLS) соединение зашифровано, и политика соблюдена; с ldap:// без шифрования сервис и сам работать откажется. «Привязка канала LDAP» (LdapEnforceChannelBinding) относится к входу по Kerberos и NTLM поверх TLS; сервис использует простую привязку по LDAPS, на которую она не действует. Ослаблять эти политики ради сервиса не нужно.

Как это устроено и что учесть#

  • Локальный или доменный. Логин, занятый в сервисе локальной учётной записью (и admin), проверяется только в сервисе — его пароль в домен не уходит. Все остальные логины проверяет только домен. Локальная учётная запись сама доменной не становится: её привязывает администратор сервиса. Человек с логином admin в домене войти в сервис под ним не сможет.
  • Список пользователей. В колонке «источник» — «локальный» или «домен» и когда домен последний раз подтвердил человека. Доменной записи нельзя задать пароль или выслать ссылку. Её можно убрать из сервиса, но при следующем входе она заведётся снова (без прежних прав), если человек остался в группе доступа: чтобы закрыть вход, уберите его из группы в домене.
  • Роль администратора. Если задана LDAP_ADMIN_GROUP, роль доменным пользователям даёт и снимает только группа. Не задана — роль ставится галочкой на странице.
  • Программы и ИИ-клиенты. Человек с доменной учётной записью выпускает себе ключ доступа (меню учётной записи). Логином и паролем домена в запросе (HTTP Basic) сервис не пускает: доменному паролю не место в файлах настроек. Логин и пароль в запросе — только для локальных учётных записей.
  • Если домен недоступен. Войти доменным логином нельзя: «домен сейчас не отвечает». Те, кто уже вошёл, продолжают работать по последней сверке с доменом — не дольше 4 часов, потом сервис просит подождать ответа домена. admin и локальные учётные записи входят всегда.
  • Заявки на доступ и «Забыл пароль» остаются для локальных учётных записей; доменной они не нужны.
  • С самого сервера по HTTP. Запрос с адреса 127.0.0.1 считается защищённым. В Docker так выглядит только запрос изнутри контейнера; если перед сервисом стоит свой прокси на том же сервере без шифрования — доменный вход через него включать нельзя.
  • Имя человека для сервиса — его sAMAccountName. Если в домене логин не из латинских букв, цифр, точки, дефиса и подчёркивания, начинается не с буквы или цифры или длиннее 32 знаков, войти под ним нельзя.

Что проверено: всё описанное — на контроллере домена Samba 4 (совместим с Active Directory) с собственным центром сертификации и на прокси Caddy с внутренним сертификатом. На настоящем Active Directory под Windows Server не проверялось — первым делом нажмите «Проверить подключение».

11. Несколько записей одновременно#

WORKERS в .env — сколько записей обрабатывается сразу; по умолчанию 3, 1 — строго по одной. Остальные ждут в очереди.

  • Сервер это почти не нагружает: обработка — ожидание ответа провайдера. Нагружает только извлечение звука из видео, и оно идёт не более чем для двух записей сразу при любом WORKERS.
  • На расходы не влияет: платится за минуты звука и объём текста, а не за скорость.
  • Больше 5 ставить незачем: провайдер начнёт отвечать «слишком много запросов» (сервис это пережидает сам, но выигрыша во времени не будет). Пределы поставщика при 3–5 записях одновременно на практике не измерялись.

Очередь и ручной запуск#

Всё это — на странице «Управление → Обработка».

  • «Снять из очереди» — у записи, прогон которой ещё не начался, с подтверждением. Снятая сама в очередь не вернётся — и после перезапуска сервиса, — пока её файл не изменится или её не запустят вручную. Снятые видны там же, в блоке «Очередь и ожидание».
  • «Отменить прогон» — у записи в работе, с подтверждением. Идущий запрос поставщику не обрывается: поставщик мог уже выполнить работу и списать деньги. Прогон останавливается перед следующим платным запросом — от секунд до нескольких минут. Оплаченное до отмены остаётся в расходах и на диске: запуск заново возьмёт готовое без новой оплаты. По расписанию отменённая запись не повторяется, писем о ней нет; готовая прежде запись остаётся готовой.
  • Ручной запуск берёт только записи из списка входной папки: медиафайл не из корзины (.trash) и не из недогрузок (.uploads), не временный (.part, .tmp, .crdownload). Путь с .. или . — отказ. Файл ещё дописывается — отказ 409: сервис возьмёт его сам, когда он перестанет меняться.
  • Отложенные файлы. Некоторые файлы сервис сам в обработку не берёт, а показывает в блоке «Очередь и ожидание» с пометкой «отложен: …» и в списке записей у людей — «отложена»: файл похож на недокопированный (копия по сети замерла посреди файла: заголовок обещает больше, чем лежит на диске) или это копия уже обработанной записи с тем же содержимым. Распознавание такого файла стоило бы денег впустую. Нужен — запустите его вручную; не нужен — уберите файл. Похожий на недокопированный файл, который потом изменился (докопировали), сервис берёт сам.
  • Отметка «сервис жив». Сервис раз в 30 секунд отмечается в базе; вверху раздела видно, сколько секунд назад была отметка, сколько он работает и сколько обработчиков живо. Давняя отметка или остановившийся обработчик — тревожная пометка со словами.

12. Резервная копия и восстановление#

Коротко: раз в сутки — копия всей установки одним архивом без остановки сервиса: по расписанию из самого сервиса (страница «Обработка») или командой из планировщика системы; раз в месяц — проверка, что из архива действительно можно восстановиться. Файлы настроек (.env, compose.yml) копируются отдельно: сервис их не видит.

Требование к папке состояния. Папка state (HOST_STATE) должна лежать на локальном диске сервера. Базу на сетевой папке (SMB, NFS, сетевой диск Windows) держать нельзя: блокировки файлов там работают не всегда, и при обрыве связи база может повредиться. Сервис проверяет это при запуске: сетевую папку называет в журнале работы и на странице «Обработка», а папку, которая не держит блокировку вовсе, отказывается использовать и не запускается. Из контейнера видно не всё: сетевой диск, который Windows показывает Docker Desktop под буквой (Z:\), отсюда неотличим от локального — за это отвечаете вы. Папки inbox и outbox на сетевом диске допустимы: в них обычные файлы. Папку для копий (HOST_BACKUP) лучше как раз вынести на другой диск или в сеть.

Docker Desktop (Windows, macOS) подключает папки компьютера через прослойку, а не напрямую. База на ней работает — проверено на Windows с папкой на диске C: (запись, одновременная копия, обрыв процесса посреди транзакции), — но медленнее, чем на Linux. Для постоянной работы организации ставьте сервис на Linux.

Копия по расписанию из самого сервиса#

Проще всего — расписание на странице «Управление → Обработка», раздел «Резервная копия»:

  • время — по часовому поясу сервиса (TZ в .env), каждый день или раз в неделю в выбранный день;
  • с исходными записями (папка inbox) или без них — без них архив в разы меньше, но записи из него заново с распознаванием не обработать (что теряется — в таблице выше);
  • держать копий — от 1 до 365 (по умолчанию 7): после каждой новой копии самые старые сверх этого числа стираются.

Сервис был выключен в назначенное время — когда он снова заработает, будет одна копия: пропущенные пачкой не догоняются. Копия не удалась — следующая попытка снова по расписанию, а вверху раздела «Обработка» висит плашка «Резервная копия не сделана» с причиной, пока следующая копия не удастся; в журнале работы — строка ВНИМАНИЕ: резервная копия НЕ сделана: …. Кнопка «Сделать копию сейчас» делает копию в фоне с теми же настройками; обработка записей при этом идёт. Две копии сразу сервис не делает: пока идёт одна, кнопка ждёт.

Архив и опись — те же, что у команды ниже, в той же папке копий (HOST_BACKUP); какой копия была — по расписанию, по кнопке или командой — видно на странице и в журнале действий. Расписание, кто и когда его сохранил, хранится в базе. Файлы настроек (.env, compose.yml) копия из сервиса тоже не видит — их копируют отдельно (ниже).

Планировщик системы (ниже) остаётся вариантом — например, чтобы ночные копии без записей и недельные полные лежали в разных папках. Его несостоявшаяся копия тоже видна плашкой на «Обработке». Не включайте оба на одно время: совпав, одна из копий откажет (готовый архив другой не пострадает).

Копия без остановки — встроенная команда#

Папку для архивов задаёт HOST_BACKUP в .env (по умолчанию — backup в рабочей папке; лучше другой диск: копия на том же диске не спасёт, когда диск откажет). Если compose.yml у вас от версии без базы, возьмите новый из комплекта: в нём появилась строка с HOST_BACKUP. После правки — docker compose up -d.

Команда одна и та же на Linux и в PowerShell, выполняется в рабочей папке:

bash
docker compose exec podyachiy python -m app.backup create

Сервис при этом работает: люди входят, записи обрабатываются. Команда снимает согласованный снимок базы средствами самой базы, затем складывает в архив остальное из state, prompts, outbox и inbox. Итог — два файла в папке копий:

podyachiy-backup-20261010-235703.tar                  архив
podyachiy-backup-20261010-235703.tar.manifest.json    опись: версия сервиса и схемы базы, состав,
размер и контрольная сумма каждого файла,
число пользователей, записей, событий, расходы

Опись лежит и внутри архива. Команда печатает итог, пишет его строкой в журнал работы (outbox\_logs\podyachiy.log) и событием в журнал действий; на странице «Обработка» в разделе «Резервная копия» видно, когда была последняя копия. Код завершения: 0 — копия сделана, 1 — не сделана (причина — в выводе и в журнале работы), 2 — сделана, но какие-то файлы не прочитались (они названы).

Параметры:

ПараметрЧто делает
--no-inboxкопия без исходных записей. Архив меньше в разы. Что теряется — в таблице выше: исходное видео и повторное распознавание; протоколы и звук в копии есть
--keep Nпосле удачной копии оставить N последних архивов в папке, остальные стереть
--to ПАПКАположить архив в другую папку внутри контейнера (она тоже должна быть подключена с сервера)
bash
docker compose exec podyachiy python -m app.backup create --no-inbox --keep 14

Чего стоит знать:

  • Запись, обработка которой закончилась, пока шла копия, попадает в архив результатами, но не строкой базы: снимок базы снимается первым. После восстановления сервис возьмёт такую запись снова — расшифровку возьмёт с диска, заново сделает только протокол. Поэтому копию по расписанию ставьте на ночь.
  • Файлы, которые менялись, пока их читали (обычно это лог), в архив попадают такими, какими успели прочитаться; команда их перечисляет.
  • Недогруженные файлы (inbox\.uploads) в копию не идут.

Настройки — отдельным шагом. .env и compose.yml лежат на сервере вне контейнера, и команда их не видит. Скопируйте их рядом с архивами — после каждой правки настроек.

Windows (PowerShell):

PowerShell
Copy-Item C:\Podyachiy\.env, C:\Podyachiy\compose.yml E:\Backup\Podyachiy\ -Force

Linux:

bash
cp /opt/podyachiy/.env /opt/podyachiy/compose.yml /backup/podyachiy/

При HTTPS — ещё Caddyfile и папки certs и caddy.

Копия с остановкой — просто скопировать папки#

Годится, если встроенная команда почему-то недоступна. Сервис на время копирования останавливают:

Windows (PowerShell):

PowerShell
cd C:\Podyachiy
docker compose stop
robocopy state   E:\Backup\Podyachiy\state   /MIR /R:2 /W:5
robocopy outbox  E:\Backup\Podyachiy\outbox  /MIR /R:2 /W:5
robocopy inbox   E:\Backup\Podyachiy\inbox   /MIR /R:2 /W:5
robocopy prompts E:\Backup\Podyachiy\prompts /MIR /R:2 /W:5
Copy-Item .env, compose.yml E:\Backup\Podyachiy\ -Force
docker compose start

Linux:

bash
cd /opt/podyachiy
docker compose stop
rsync -a --delete state outbox inbox prompts .env compose.yml /backup/podyachiy/
docker compose start

Почему базу нельзя копировать «на ходу». Пока сервис работает, свежие изменения лежат не в самом файле podyachiy.db, а рядом — в podyachiy.db-wal. Обычное копирование читает файлы по очереди и в разное время: в копию попадает половина изменения, и такая база либо не откроется, либо молча потеряет часть данных. У остановленного сервиса файл базы один и целый. Если после остановки рядом с базой остались файлы -wal и -shm, копируйте все три. Встроенная команда этой беды не имеет: снимок делает сама база.

Ключи /MIR и --delete делают копию точным зеркалом: удалённое в сервисе исчезнет и из копии при следующем запуске. Истории у такой копии нет — у архивов встроенной команды она есть.

Расписание в планировщике системы и сколько копий хранить#

Правило «3-2-1»: три копии данных, на двух разных носителях, одна — вне здания. Рабочая установка — первая, папка копий на другом диске — вторая, выгрузка архивов в хранилище организации — третья.

Разумный порядок: каждую ночь — копия без исходных записей, хранить 14 штук; раз в неделю — полная, хранить 4. Исходные записи большие и не меняются: полной копии раз в неделю достаточно. --keep (и «держать копий» в расписании сервиса) считает все архивы папки вместе, поэтому ночные и недельные кладите в разные папки (--to) либо храните одним числом. Одно расписание — проще на странице сервиса (выше); ниже — то же планировщиком системы.

Linux — crontab -e от пользователя, которому можно docker:

# каждую ночь в 02:30 — копия без исходных записей, 14 последних
30 2 * * * cd /opt/podyachiy && docker compose exec -T podyachiy python -m app.backup create --no-inbox --keep 14 >> /var/log/podyachiy-backup.log 2>&1

Windows — Планировщик заданий. Команда, которую запускает задание (сохраните файлом C:\Podyachiy\backup.cmd):

cd /d C:\Podyachiy
docker compose exec -T podyachiy python -m app.backup create --no-inbox --keep 14 >> backup.log 2>&1

и само задание (PowerShell от администратора, один раз):

PowerShell
schtasks /Create /TN "Podyachiy backup" /TR "C:\Podyachiy\backup.cmd" /SC DAILY /ST 02:30 /RU SYSTEM

Ключ -T обязателен: у задания по расписанию нет окна. Docker Desktop на Windows запускается при входе пользователя — задание от SYSTEM сработает, только когда Docker запущен; на сервере без входа пользователя ставьте сервис на Linux. Несделанная копия оставляет в журнале работы строку ВНИМАНИЕ: резервная копия НЕ сделана: причина и плашку на странице «Обработка», сделанная — резервная копия сделана: …; дата последней копии видна там же. Заглядывайте туда: расписание, которое молча перестало работать, — обычная история. Задание, которое вовсе не запустилось (выключен Docker, удалено задание), плашки не оставит — видно только по дате последней копии.

bash

Без имени проверяется последний архив в папке копий; можно назвать любой: … verify /data/backup/podyachiy-backup-20261010-235703.tar (путь — внутри контейнера: папка копий там называется /data/backup). Восстановление на чистом сервере#

Нужно: архив, его опись (не обязательна, но с ней проверка строже), сохранённые .env и compose.yml.

  1. Установите Docker (раздел 2) и создайте рабочую папку, например C:\Podyachiy или /opt/podyachiy. Папка должна быть пустой: поверх существующей установки архив не разворачивается.
  2. Положите в неё .env и compose.yml из копии (при HTTPS — Caddyfile, certs, caddy). На другом сервере проверьте в .env пути HOST_… и адрес PUBLIC_URL.
  3. Создайте в ней папку backup (или ту, что названа в HOST_BACKUP) и положите туда архив и его опись.

  4. Разверните архив. Сервис при этом не запущен; команда запускает одноразовый контейнер:

    bash
    docker compose run --rm --no-deps podyachiy python -m app.backup restore /data/backup/podyachiy-backup-20261010-235703.tar

    Команда сначала проверяет архив целиком (как verify), затем раскладывает файлы по папкам state, outbox, inbox, prompts и сверяет каждый с описью ещё раз. Работающий над этой папкой сервис и оставшиеся в state файлы podyachiy.db-wal, -shm, -journal от прежней базы — отказ: SQLite применил бы их к восстановленной базе и испортил бы её. Ответ:

    установка восстановлена из архива podyachiy-backup-20261010-235703.tar (сделан 2026-10-10T23:57:03+03:00,
версия сервиса 1.0.0): файлов 175, 2.0 МБ; пользователей 7, записей 17, событий 551, расходы 5.14 $
  5. Запустите сервис: docker compose up -d. В журнале работы (docker compose logs) должна быть строка база: /data/state/podyachiy.db, схема … и не должно быть строк ОТКАЗ ЗАПУСКА.

  6. Проверьте:

    • войдите под admin и под обычным пользователем — пароли прежние; входы в браузерах, сделанные до копии, тоже действуют (ключ подписи восстановлен);
    • откройте любую запись: протокол, расшифровка, карта; если в копии был звук — проигрыватель играет;
    • «Управление → Расходы»: итог тот же, что в строке ответа команды;
    • «Поручения»: отметки «выполнено» и сроки на месте;
    • ключ доступа: curl -H "Authorization: Bearer <ключ>" http://localhost:8081/api/v1/whoami (в PowerShell — curl.exe) отвечает именем владельца — ключи выпускать заново не нужно.

Версии. Номер версии сервиса и схемы базы записан в описи.

  • Архив старее сервиса (сделан до обновления) — разворачивается; схему базы сервис доведёт сам при запуске, в журнале работы будет строка схема базы обновлена: версия N → M.
  • Архив новее сервиса — команда откажет: архив сделан более новой версией сервиса. Впишите в .env номер той версии (IMAGE_TAG) или новее и повторите.
  • Копия папок, сделанная до перехода на базу (с файлами users.json, processed.json), — это не архив команды: верните папки как есть и запустите сервис, он перенесёт их в базу (раздел 13).

Возвращайте inbox и outbox из одной копии. Сервис решает, обработана ли запись, по базе. Если в inbox окажутся записи, которых нет в базе (копия inbox свежее), сервис обработает их как новые — за деньги.

Частные случаи#

Перенос на другой сервер. То же, что восстановление. На старом сервере дождитесь, пока очередь обработки опустеет, сделайте копию (python -m app.backup create) и остановите сервис (docker compose stop) — чтобы после копии ничего не изменилось. На новом — шаги 1–6. Старый сервис больше не запускайте: две установки с одной входной папкой обработают каждую запись дважды.

Вернуть одну случайно удалённую запись. Первые 30 дней удалённая запись возвращается кнопкой «Корзина» на странице записей — со всем, что у неё было (раздел 15). Срок корзины вышел — запись возвращают из архива, сделанного, когда она ещё была, — вместе со строкой журнала обработки, отметками поручений и словарём записи. Сервис на это время останавливают: с работающим команда откажет — свою запись в базу он бы не увидел и следующей своей записью затёр бы:

bash
docker compose stop
docker compose run --rm --no-deps podyachiy python -m app.backup record /data/backup/podyachiy-backup-20261010-235703.tar "Проекты/Склад/2026-08-27 Старт проекта адресного хранения.mp4"
docker compose start

Путь записи — каким он был: папка и имя файла с расширением (он виден в журнале действий, в событии об удалении). Команда кладёт на место исходник (если он есть в архиве) и папку результатов outbox\<папка>\<имя записи>\, а в базу возвращает строки таблиц records (журнал обработки), marks (отметки и сроки поручений), dictionaries (словарь записи) и uploads (кто загрузил). Расходы записи при удалении из журнала не уходили. Если на месте записи уже что-то лежит, команда откажет и ничего не тронет.

Откат неудачного обновления. Два способа.

  • Архив, сделанный перед обновлением: остановите сервис, уберите папки state, outbox, inbox, впишите в .env прежний номер версии (IMAGE_TAG) и восстановите архив (шаги 4–6). Потеряется то, что сделано после копии.
  • Обновление было переходом на базу, а архива нет: прежние файлы состояния сервис сложил в state\до-базы-<дата> (раздел 13) — их возвращают на прежние места, а базу убирают. Команды — в разделе 13, «Вернуться на версию без базы».

Повреждённая база. Сервис не запускается, в журнале работы: ОТКАЗ ЗАПУСКА: база /data/state/podyachiy.db повреждена: …. Сервис базу не чинит и не заводит пустую взамен. Порядок действий:

  1. Остановите сервис и сохраните повреждённые файлы state\podyachiy.db* в сторону — не удаляйте.
  2. Возьмите последний архив и разверните его в новую рабочую папку (шаги 1–5), затем перенесите в неё из старой то, что новее архива: содержимое inbox и outbox. Записи, появившиеся после копии, сервис обработает заново — расшифровки возьмёт с диска.
  3. Если архивов нет: рядом может лежать state\до-базы-<дата> — состояние на день перехода на базу. Иначе базу придётся завести заново (убрать файлы podyachiy.db* и папку до-базы-…): пользователи, права и расходы потеряны, а записи из inbox пойдут в обработку заново. Чтобы не платить повторно, перед запуском уберите исходные записи из inbox.

Причина повреждения почти всегда одна из трёх: диск, отключение питания на дешёвом диске без защиты записи, папка состояния на сетевой папке.

Чего копия не содержит#

  • .env, compose.yml, Caddyfile, certs, caddy — копируются отдельно (выше);
  • недогруженные файлы inbox\.uploads;
  • сам образ сервиса: он скачивается заново (docker compose pull); номер версии — в описи;
  • очередь обработки: записи, которые ждали обработки, сервис найдёт в inbox сам;
  • лог контейнера (docker compose logs); лог сервиса outbox\_logs в копии есть.

13. Обновление версии#

bash
docker compose pull
docker compose up -d

Образ можно собрать и самому — из исходников репозитория: docker build -t egordoronchenko/podyachiy .

Записи, результаты, база с пользователями и расходами, шаблоны и настройки при обновлении не затрагиваются: они лежат в папках на сервере, а не в контейнере. Схему базы новая версия при необходимости обновляет сама при запуске. Шаблоны в prompts, которые вы правили, новая версия не перезаписывает — но и новые версии шаблонов сама не подставит. Чтобы взять шаблон из новой версии, откройте его в разделе «Управление → Настройки»: «Показать стандартный рядом» покажет текст новой версии, «Вернуть стандартный» запишет его (ваш текст останется в прошлых версиях). Номер установленной версии — в меню «О сервисе».

Перед обновлением сделайте резервную копию (раздел 12): docker compose exec podyachiy python -m app.backup create, а на версии без этой команды — копию папок с остановкой.

Обновление до 1.2.0: что заметят люди и администратор#

Команды те же (docker compose pull, docker compose up -d). Схема базы при первом запуске обновится сама до версии 3 — в журнале работы строка схема базы обновлена: версия 2 → 3; вернуться на 1.1.x можно только вместе с базой из копии, сделанной перед обновлением.

  • Все войдут заново. Метка входа теперь подписана по-новому, и прежние входы в браузерах перестают действовать. Пароли и ключи доступа не меняются. Предупредите людей.
  • Напоминания о сроках поручений включены у всех, у кого в учётной записи есть почта (раздел 8, «Напоминания о сроках поручений»): первые письма уйдут в первый же день после 8:00 по часам сервиса — обновили днём, значит, через минуту после запуска. Отключает каждый сам — меню под именем → «Напоминания о сроках». Если они не нужны, предупредите людей заранее.
  • Без тома outbox сервис не запускается (ОТКАЗ ЗАПУСКА: папка результатов … не подключена с хоста). Если вы убирали из compose.yml строку с HOST_OUTBOX, верните её — или возьмите compose.yml из комплекта и перенесите в него свои правки.
  • За прокси, который меняет заголовок Host, нужен PUBLIC_URL — иначе действия на странице получат отказ 403 «запрос пришёл со страницы другого сайта» (раздел 4). Caddy из комплекта Host не меняет.
  • MAIL_DOMAINS ограничивает теперь и почту в заявке на доступ. Не задан — предупреждение в журнале работы и в блоке «Почта» раздела «Пользователи» (раздел 8).
  • Шаблоны. Нетронутые стандартные шаблоны сервис при запуске переводит на общие правила из prompts/common.md (раздел 7а) — текст для модели тот же; строка в журнале работы шаблоны … переведены на общие правила из common.md. Шаблоны, которые вы правили, остаются как были. Свой тип записи с ключом common в types.json больше не считается типом: это имя занял общий файл.
  • Имена с «ё» и «й» от macOS. Записи и папки, имена которых macOS записала в разложенной форме Unicode, сервис один раз при запуске приводит к обычной (составной) — строкой в журнале на каждую; результаты, журнал, права и словари переезжают под новое имя.
  • Записи, удалённые до 1.2.0, тоже возвращаются кнопкой «Корзина», но без словаря, прав на папку и автора загрузки: их опись этого не хранила.
  • Переименование мимо сервиса. Записи, обработанные до 1.2.0, не знают отпечатка своего файла: такую запись, переименованную или перенесённую прямо на диске, сервис не узнает, а отложит файл (раздел 11, «Отложенные файлы») — верните файлу прежнее имя и переименуйте запись на странице.

Обновление с версии без базы#

До этой версии состояние сервиса лежало отдельными файлами: state\users.json, keys.json, dictionaries.json, settings.json, requests.json, journal.jsonl, brand\brand.json, outbox\_state\processed.json и файлы отметок поручений *.tasks.json в папках результатов. Теперь всё это — в одной базе state\podyachiy.db. Переносить руками ничего не нужно: первый запуск новой версии делает это сам. Порядок:

  1. Сделайте копию папок с остановкой (раздел 12, «Копия с остановкой») — как минимум state, outbox и .env.
  2. Возьмите из комплекта новый compose.yml: в нём появилась папка для резервных копий (HOST_BACKUP). Свои правки (HTTPS, сеть) перенесите в него. Проверьте, что строка с HOST_STATE на месте и что папка state лежит на локальном диске сервера: без неё новая версия не запустится — в ней база.
  3. docker compose pull, затем docker compose up -d.

  4. Откройте журнал работы (docker compose logs или outbox\_logs\podyachiy.log). В нём должны быть три строки:

    первый запуск версии с базой: переношу состояние из файлов (users.json, keys.json, …) в /data/state/podyachiy.db
перенос в базу завершён за 0.3 с, сверка сошлась: пользователей — 7, прав на папки — 10, ключей доступа — 2, словарей — 1, заявок — 0, записей в журнале обработки — 17, отметок и сроков поручений — 58, событий — 154, из них прогонов — 32; расходы по журналу — 5.31 $ (до и после переноса совпадают)
прежние файлы состояния убраны в /data/state/до-базы-2026-10-10 — копия на случай отката, сервис их больше не читает

    Сверка — не формальность: всё перенесённое читается из новой базы обратно и сравнивается с прочитанным из файлов — каждый пользователь, право, ключ, словарь, заявка, строка журнала обработки, отметка, каждое событие журнала и итог расходов по валютам. Если сервис не запустился, в журнале работы есть строка ОТКАЗ ЗАПУСКА: … с причиной (типовые — в разделе 14). Второй раз перенос не выполняется: когда база есть, файлы прежнего вида сервис не читает.

Вернуться на версию без базы#

Только пока в новой версии не сделано ничего ценного: прежние файлы — состояние на момент перехода, всё сделанное после него в них не попадёт, а записи, обработанные после перехода, прежняя версия обработает заново.

Windows (PowerShell), в рабочей папке:

PowerShell
docker compose down
New-Item -ItemType Directory state\база-новой-версии | Out-Null
Move-Item state\podyachiy.db* state\база-новой-версии\
$old = (Get-ChildItem state -Directory -Filter "до-базы-*" | Sort-Object Name | Select-Object -Last 1).FullName
robocopy "$old\outbox" outbox /E
robocopy $old state /E /XD outbox /XF ПРОЧТИ.txt

Linux:

bash
docker compose down
mkdir state/база-новой-версии && mv state/podyachiy.db* state/база-новой-версии/
old=$(ls -d state/до-базы-* | tail -1)
cp -a "$old/outbox/." outbox/
find "$old" -mindepth 1 -maxdepth 1 ! -name outbox ! -name ПРОЧТИ.txt -exec cp -a {} state/ \;

Затем впишите в IMAGE_TAG в .env номер версии, стоявшей до перехода, и выполните docker compose up -d. Версии без базы — только до 1.0.0: начиная с 1.0.0 база есть в каждой.

После обновления с версии до 1.0.0: загрузка — отдельное право. Уже выданное «чтение» теперь означает только чтение, а загрузки в личную папку нет ни у кого, кроме администраторов сервиса. Администраторы папок загружают, как прежде. Остальным загрузку выдайте заново: «Папки и доступ» → «Доступ» → столбец «загрузка»; для личной папки — «Пользователи» → «Изменить» → «Загрузка в личную папку». Переключателя «как раньше» нет.

Закрепить версию. С IMAGE_TAG=latest команда pull берёт самую свежую сборку. Чтобы обновляться только намеренно, впишите в .env номер версии: IMAGE_TAG=1.2.0.

Вернуться на прежнюю версию: впишите в IMAGE_TAG её номер и выполните docker compose up -d. Схему базы новая версия могла обновить (строка схема базы обновлена в журнале работы) — тогда прежняя версия откажется запускаться (база … от более новой версии сервиса): вместе с версией верните и базу из копии, сделанной перед обновлением (раздел 12). На версию без базы — см. выше.

15. Корзина и сроки хранения#

  • Сам сервис ничего не удаляет по сроку. Записи, звук и протоколы лежат, пока их не удалит человек. Автоматического «хранить N месяцев» нет: за местом на диске следит администратор.
  • Удаление записи или папки на странице — это перенос в корзину. Файлы уходят в папки inbox\.trash и outbox\.trash и лежат там 30 дней, затем стираются сами (проверка — при запуске и раз в сутки). Каждая корзина чистится сама по себе: если папка inbox подключена только для чтения, корзина в outbox чистится всё равно, а о корзине, которую стереть не удалось, в журнале работы появляется одна строка — корзина входной папки не чистится: причина.
  • Вернуть удалённое — кнопкой «Корзина» на странице записей, пока не вышли 30 дней. Окно показывает, что человек может вернуть: запись — хозяин её папки (владелец личной, администратор общей, администратор сервиса), папку — администратор сервиса. «Вернуть» кладёт запись или папку на прежнее место со всем, что было: протокол, расшифровка, подписи говорящих, строка журнала обработки, отметки и сроки поручений, словарь, права на папку, авторы загрузок, расходы. Заново ничего не обрабатывается и не оплачивается. Возврат записывается в журнал действий.
  • Прежнее место занято — отказ 409: запись или папку с тем же именем сначала переименуйте или перенесите. Папки, в которой лежало удалённое, больше нет — сначала верните её (или создайте заново под тем же именем). Право на папку не возвращается учётной записи, которую с тех пор удалили.
  • Удалённое до версии 1.2.0 тоже возвращается кнопкой, но без словаря, прав на папку и автора загрузки: их опись этого не хранила (в окне корзины так и написано).
  • Срок корзины вышел — запись возвращают из резервной копии, сделанной, когда она ещё была: команда python -m app.backup record (раздел 12, «Вернуть одну случайно удалённую запись»).
  • Вернуть вручную — запасной путь, если опись в корзине не читается (окно корзины так и скажет). В outbox\.trash\<дата-время>\ лежит файл удалено.json: что и откуда убрано, строки журнала обработки (records) и отметки поручений (marks), какими они были. Остановите сервис, переложите файлы из обеих корзин (inbox\.trash и outbox\.trash) на прежние места и запустите сервис. Строк в базе при этом нет, поэтому сервис сочтёт запись новой и обработает её снова: расшифровку возьмёт с диска, заново сделает (и оплатит) только протокол; отметки поручений придётся поставить заново — по файлу удалено.json. Без исходника в inbox запись в список не вернётся.
  • Освободить место раньше срока: удалите содержимое inbox\.trash и outbox\.trash вручную.
  • Недогруженные файлы (человек начал загрузку и бросил) лежат в inbox\.uploads неделю и стираются сами.
  • Расходы на удалённые записи остаются в отчёте: журнал расходов удаление не трогает.
  • Папка удалённого пользователя остаётся на диске в inbox\Пользовательские\<логин>; её удаляют вручную, если записи больше не нужны.

16. Чего сервис не делает#

  • Поддержки и гарантий нет: сервис распространяется бесплатно и «как есть» (лицензия MIT). Вопросы и предложения автору — по контактам в меню «О сервисе» или в разделе Issues репозитория: автор отвечает по возможности, срок ответа не гарантируется. К сообщению об ошибке приложите сведения, которые копирует кнопка в этом разделе (версия, режим, модель, браузер); записи совещаний и ключи не присылайте.
  • Не работает без интернета и без поставщика моделей (RouterAI или OpenRouter). Записи обрабатываются внешними моделями; варианта «всё внутри организации» нет.
  • Не шифрует сам. HTTPS даёт прокси (раздел 10); файлы на диске не зашифрованы.
  • Не защищает папки на диске. Права действуют на странице; кто имеет доступ к inbox и outbox на сервере или по сети, читает всё.
  • Не входит без ввода пароля (единый вход, SSO, Kerberos). Войти логином и паролем домена можно (раздел 10а), но вводить их на странице входа нужно каждому; без домена у сервиса свои логины и пароли.
  • Не узнаёт людей по голосу. Голоса различаются, имена подписывает человек.
  • Не гарантирует точность. Протокол пишет языковая модель: поручения иногда теряются, фамилии и термины искажаются. Важное сверяют по записи — см. справку, «Насколько этому верить».
  • Не удаляет старое по сроку. О месте на диске только предупреждает — когда свободно меньше 2 ГБ (раздел 3).
  • Не выносит копии за пределы сервера. Копию по расписанию сервис делает сам (раздел 12), но кладёт её в папку копий; унести архивы на другой носитель и вне здания — задача администратора.
  • Не рассылает протоколы сам и не ставит задачи в трекеры: протокол на почту отправляет человек кнопкой в записи (раздел 8), остальное читают на странице, скачивают файлом (DOCX, PDF, HTML, календарь ICS) или забирают запросами /api/v1 (все методы — на странице /api); о готовой записи внешней системе сообщает webhook (раздел 9а).
  • Не рассчитан на публикацию в интернете.
